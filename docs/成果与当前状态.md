# 工作流成果、当前状态与已解决的问题

更新：2026-09-13。公开仓库：https://github.com/flameyc/xianyu-ppt-workflow 。访问链接不需要仓库成员权限，公开内容也可能被搜索、下载和复制。客户聊天、附件、订单和模板库留本机。

## 完成结果

目前做成的是一个由本人和Codex协作运行的半自动PPT制作工作区。已有流程：登记需求 → 归档资料 → 核对事实和缺项 → 查找模板 → 制作并登记版本 → 检查和局部修改 → 本地交付包 → 记录收款与候选经验。实际消息发送、客户验收、审美和业务判断仍需本人参与。

| 成果 | 实际完成范围 |
|---|---|
| 跨会话接力 | GitHub保存代码、技能、执行计划、状态和接手约定；新会话先读CURRENT_STATE.md |
| 大素材库检索 | 235.845GB、4842份PPT/PPTX的本地文件名索引，按需返回少量候选；尚非全库视觉理解 |
| 订单资料管理 | 本地快照、哈希去重、解析缓存、来源和缺项、精简任务包；新事实触发旧版本复核 |
| 制作与修改 | 现有PPT原生文本精确修改；教学类新布局生成；版本不覆盖，审核绑定文件指纹 |
| 两条制作路线 | 默认按计费单价建议省Token或追加定制投入；两路线都保留审美目标，简单单可低成本超预期 |

| 案例与经验 | 5页内部演示闭环、教学案例两份22页内部重制、首单成功与返工复盘；候选经验进入订单 |
| 检查 | 最近33项测试通过，覆盖工作流、路由和仓库边界；测试不代表客户视觉满意 |

## 当前状态

制作基础流程已能运行，但尚未成为无人值守的接单赚钱系统。此前两份22页重制稿虽通过当时结构与渲染检查，用户指出制作效果不足；复盘发现未充分延续客户已认可的生动插画方向。原教案找回后，两版均已标记需要重新审核，不能当作客户终稿。

尚未完成：真实网页PPT样稿发送、生成/下载、可编辑接回与验收的完整验证；实际Token/人工成本比较；客户软件中的编辑与显示验证；实时消息监听、自动接待、自动发送、投流联动。历史首单好评及转介绍不等于新版系统已完成真实新单验证。

## 搭建过程中已经解决或明确处理的问题

| 原问题 | 当前处理 | 剩余验证 |
|---|---|---|
| 换会话容易丢进度 | 专用仓库＋当前状态＋唯一执行计划＋接手约定 | 新机器仍需本地依赖和订单资料 |
| 200多GB模板怕每次读爆Token | 文件名索引、限量候选、解析缓存；文件体积不直接等于模型输入 | 少量关键页视觉缓存尚待完善 |
| 聊天、附件、版本分散 | 来源快照、订单隔离、任务包和事实版本 | 微信增量读取和附件关联继续完善 |
| 改稿容易改错版本或丢内容 | 文件哈希、稳定版本、局部修改、章节页码映射要求 | 跨真实订单观察漏改率 |
| 全页图片难编辑 | 原生文字/形状与复杂插画分层，提前确认编辑边界 | 不能将所有插画恢复为可编辑矢量 |
| AI先创作文案，后来与教案冲突 | 先锁定来源，标题/环节按客户要求，创意与事实分开 | 每单仍需逐页内容核对 |
| 低价路线被理解为低视觉质量 | 两路线共享风格标准，省成本靠复用与局部改稿 | 实测超预期的投入与客户反馈 |
| 整套做完才发现方向错误 | 先封面＋代表内容样页，再锁定风格扩展 | 样稿确认当前由Codex维护，非程序强制闸门 |
| 全部工作挤在Codex长上下文 | 网页样稿合同、最小交接包、独立素材与恢复记录 | 不宣称已测得节省百分比 |
| 每单经验停留在聊天中 | 观察、动作、结果、下次验证四项记录；跨单验证后再推广 | 暂无多单成本或返工改善统计 |
| 分享项目可能带出客户资料 | 源码/抽象经验与私有运行数据分开，提交边界检查 | 每次提交继续审查；公开仓库不是客户文件同步盘 |

## 下一步

优先选择真实新单或现有案例的代表页，按客户认可方向完成样稿；确认后扩展全套，再经过真实反馈、局部修改和交付，记录人工时间、可取得用量与修改轮数。这个结果通过后，再扩展实时接待和获客模块。
